- github を使うときは gh コマンドを使うこと
- 機能を実装するときは最新の main ブランチからブランチを作って PR を作ること
- PR をマージしたら最新の main を fetch し、ローカルの main を更新してチェックアウトすること
- Rust の型名は責務を表すようにすること
  - データ・値は表す内容（`Id`、`Info`、`Summary`、`Sample`、`Snapshot` など）、処理・状態・リソースを管理する型は役割（`Scanner`、`Monitor`、`Collector`、`Reader`、`Cache`、`Unwinder`、`Encoder`、`Resolver`、`Guard` など）が伝わる名前にすること
  - 補助メソッドの有無だけで分類せず、すべての型に機械的な接尾辞を付けることは求めない。
- Rust の独自処理は、データ・状態・リソースを持つ型と、それを引数に取る通常の関数に分けること
  - コンストラクタ、読み取り・変換、キャッシュ操作、収集、起動・停止も、inherent method・関連関数ではなく処理と対象が伝わる名前の関数にすること。
  - 状態更新は `&mut`、共有状態は必要な参照や `Arc` を引数に明示し、関数化のために状態全体をコピーしたりキャッシュを廃止したりしないこと。
  - `Drop`・`Default`・`From`・`Display`・Serde・`Wire` など、必要な trait 実装は維持すること。通常の関数化を避けるための trait は追加しないこと。
  - フィールドの非公開性と、ロック・所有権・キャンセル・終了処理の契約を維持すること。関連定数を型に置くことや、標準ライブラリ・依存 crate のメソッドを呼ぶことは妨げない。
- Rust の re-export は、実際の定義元が自分自身または子孫モジュールにある項目だけに限定すること
  - `pub use`、`pub(crate) use`、`pub(super) use`、`pub(in ...) use` のすべてを対象とする。
  - 親・兄弟・別のサブシステム・外部 crate で定義された型や関数は、定義元から通常の `use` で参照すること。
  - 子モジュールを経由した再公開でも、実際の定義元が範囲外なら禁止する。パスの `crate::` / `super::` という表記だけでは判定しない。
  - 引数・戻り値に共有型が登場しても、その型を再公開しない。module root の入口一覧には実際に公開する項目だけを載せ、補助型は定義元へのリンクで案内すること。
- 各 module root の `//!` は責務と、そのモジュールの外から使う入口を説明すようにすること
  - `//! # Interface` の一覧は通常ビルドでその root が公開・再公開する型・関数を対象とし、型・visibility・関数シグネチャ・定義リンクを記載すること
  - 入口のシグネチャに登場する補助型は、`src/privileged_helper/process/fds.rs` と同様にシグネチャ中の型名そのものを定義への intra-doc link にすること
  - `Shared signature types` や `Supporting types` などの補助型一覧を別行に設けないこと
  - 対象のインターフェース（re-export、型、関数シグネチャ、visibility）を変更した場合は、この一覧も更新すること
  - 子モジュール内部の関数、フィールド、列挙値、テスト専用項目は網羅的に転記しないこと
  - 公開型のメソッドの詳細、JSON の表現・フォールバックなどの契約、所有権・ロック・処理順序の注意点は定義側に記載すること
  - 理由: 固定ツールチェーン Rust 1.98.1 の rustdoc では、非公開の祖先モジュールを持つ `pub(super)` / `pub(in ...)` などの restricted re-export が、façade 側の I/F として表示されない。`--document-private-items` や `#[doc(inline)]` でもこの構成では期待する表示にならないため、入口の一覧と定義元への intra-doc link で補う。コメント内のシグネチャは自動同期されず、リンク検査でも不一致を検出できないため、対象の変更時に手動で更新する。
- C ソース・ヘッダー（BPF を含む）を変更したら `python3 scripts/format_c.py` で整形し、`python3 scripts/format_c.py --check` を実行すること
  - clang-format は `requirements-format.txt` の固定バージョンを使うこと。インストール手順は `DEVELOPMENT.md` を参照。
- procinsh を起動するときは強めの権限が必要になるので、./scripts/dev_run.sh を利用すること
- 実装が完了したら、空いているポートで修正版のサーバーを起動し、Tailscale IPv4 と localhost（127.0.0.1・::1）の両方で待ち受けること
  - `./users/akawashiro/scripts/preview_bind.sh run ./scripts/dev_run.sh <PORT>` を利用できる
  - サーバーはユーザーが確認できるよう起動したままにし、使用したポートとアクセス URL はユーザーとの会話で報告すること
  - PR のタイトル・本文・コメントには、Tailscale の IP アドレスや、その IP を含む URL を記載しないこと
  - 変更に対応する PR がマージされたら、その変更の確認用に起動したサーバーを停止すること
- テストは `bash scripts/docker_test.sh` で Docker 内で実行すること
  - Rust テストは常に必要な権限を持つ Docker コンテナで全件実行し、ignore 属性や権限不足によるスキップを使わないこと
  - Rust テストを含む通常テストは `bash scripts/docker_test.sh ordinary`、実機 eBPF は `bash scripts/docker_test.sh kernel` を使うこと
  - 通常テストは `ordinary`、静的解析は `checks`、ブラウザは `browser` suite を使うこと
  - サーバーを起動するテストもコンテナ内のビルド済みバイナリを直接実行すること
- `README.md` はユーザー向けの文書として簡潔に保ち、開発者向けの情報を書かないこと
  - 開発者向けの情報は `DEVELOPMENT.md` に記載すること。`developer-docs/` ディレクトリは作成・使用しないこと
- コメントやドキュメントでは変更履歴ではなく現在の振る舞いのみを説明すること
- PR や issue は英語で記載すること
- ARM マシンが必要な場合は zed-box-mini を使うこと。ただし zed-box-mini のカーネルバージョンは古いので QEMU + kvm を使って VM を立て、使い終わったら削除すること。
